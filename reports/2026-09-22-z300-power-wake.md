- Stored and effective `system.screen_off_timeout` were 600,000 ms (10 minutes).
- `global.stay_on_while_plugged_in=3` covered AC/USB but was inactive on battery.

At 09:50 PDT, `scripts/z300_display_power.py apply` saved the complete observed
pre-change state to `provenance/z300-display-power-backup-20260922.json`, then
set `system.screen_off_timeout=2147483647`. The script immediately read back both
the stored value and Android PowerManager's effective `Screen off timeout` as
2,147,483,647 ms while the device remained on battery, awake, and at 100%.
`stay_on_while_plugged_in` and USB configuration remained unchanged. Independent
main-session verification saved the same result in
`provenance/z300-power-independent-status-20260922.json`.

This is Android's maximum signed 32-bit timeout, approximately **24.86 days from
the last user activity**. It is a near-continuous battery display setting, not an
indefinite wakelock. `stay_on_while_plugged_in` is not presented as a battery
solution.

The Android API defines `SCREEN_OFF_TIMEOUT` as the inactivity interval before
sleep. Android 4.2 PowerManagerService reads that setting, bounds it by any
enforced device-admin limit/shorter window override, and uses it for the screen
timeout. The live admin maximum was also 2,147,483,647 and `enforced=false`. The
same source makes `STAY_ON_WHILE_PLUGGED_IN` conditional on a powered state,
matching the live `mStayOn=false`. Primary source pins and hashes are in
`provenance/z300-wake-aosp-20260922.json`:

## Wake support and limits

Android 4.2.2's `IPowerManager.aidl` defines idempotent `wakeUp(long)` as Binder
transaction 6: it wakes a sleeping device and does nothing when already awake.
The firmware's old `service` CLI accepts only `i32` and `s16`. An initial `i64`
probe was rejected with `service: unknown option i64`; it caused no display state
change and exposed a validation bug before handoff. The helper was corrected to
encode the 64-bit uptime as signed low/high `i32` Parcel words and to accept only
the exact normal reply `Result: Parcel(00000000 '....')`.

The corrected wake command was run once while the display was already awake. It
returned the exact normal Parcel reply, and before/after reads both showed
`mWakefulness=Awake`, `mScreenOn=true`, on battery, with the maximum timeout still
effective. This proves the command is accepted by this device without the toggle
race of power keycode 26. An actual screen-off to screen-on transition was not
tested because acquisitions were active; that final physical behavior remains
unverified.

Supported practical path: an authenticated network request to Opal, followed by
the existing USB ADB connection to the Z300. This can originate over Opal's Wi-Fi,
but it is not direct Wake-on-WLAN to the analyzer. It requires Opal to be reachable,
the Windows temporary ADB binary to remain present, and the analyzer USB ADB
interface to stay enumerated.

Direct analyzer Wi-Fi wake is unsupported by the examined vendor API; ADB TCP
5555 was previously verified refused, and no listener was added. The Z300 manual
documents Bluetooth for a Zebra printer and provides no remote-control or wake
profile. Bluetooth being enabled is not evidence that it can wake the display.
Read-only kernel interfaces did not expose usable Wake-on-WLAN or Bluetooth wake
capabilities. Neither direct Wi-Fi nor Bluetooth wake should be claimed.
